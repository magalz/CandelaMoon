# Maestro Setup

> The rules, definitions, and directives for the phase setup session. Bernstein executes
> this process exactly once at the start of every phase — never at the start of a task
> session. The setup session reads external context, creates the phase folder, generates
> the phase plan, and creates all individual task files.
>
> See companion documents:
> - **`maestro-workflow.md`** — task cycle and phase scaffolding.
> - **`maestro-post-phase.md`** — rules for post-phase execution.
> - **`maestro-maintenance.md`** — rules for maintenance phase execution.
> - **`maestro-orchestrator-guide.md`** — dispatch matrix, handoff protocol, review pipeline.

---

## 1. When Setup Runs

The setup session runs EXACTLY ONCE per phase. It is the very first session of a phase.
It is NOT a task session — it does not follow the task cycle, does not produce a PR,
and does not dispatch production or review agents.

Setup runs when:
- Phase N-1's post-phase session is complete AND its maintenance phase is complete.
- Bernstein is asked to begin Phase N.

Setup does NOT run:
- At the start of a task session (tasks start from the backlog).
- Mid-phase (the phase plan already exists).
- During maintenance phases (maintenance tasks come from the post-phase plan).

## 2. Setup Session Flow

```
Session Start
  │
  ├─ 1. Read global context:
  │     - Global objectives document (north star, phase strategy)
  │     - Master roadmap (phase sequence, goals, exit gates)
  │     - Previous phase's post-phase handout
  │     - Framework workflow doc (phase scaffolding rules)
  │
  ├─ 2. Read external /docs/ context:
  │     - Product spec (scope, boundaries, requirements)
  │     - Any pre-existing plans for this phase
  │     - Relevant ADRs for the phase scope
  │     - Infrastructure docs (CI architecture, policies, toolchain pins)
  │
  ├─ 3. Create phase folder in the plans directory.
  │
  ├─ 4. Generate phase plan (see §3 for structure).
  │
  ├─ 5. Create individual task files — one per task (see §4 for structure).
  │
  ├─ 6. Create the phase workspace directory.
  │
  ├─ 7. Update master roadmap with new phase status and links.
  │
  └─ 8. Produce setup handout → Session ends.
```

## 3. Phase Plan Structure

The phase plan follows the template at `maestro-templates/phase-plan.md`. It must
contain these four sections:

1. **Header**: phase number, title, status, goal, exit gate, related ADRs, dependencies.
2. **Phase Tasks**: a table of every leaf task with ID, title, status, dependencies,
   complexity, and pointer to the individual task file.
3. **Post-Phase Tasks**: a placeholder describing the post-phase session that runs
   after all Phase Tasks complete.
4. **Maintenance Phase Tasks**: a placeholder for M-tasks generated by the post-phase
   session. Initially empty.

Status values in the Phase Tasks table: `Pending` → `In Development` → `Completed`.

**Template**: `maestro-templates/phase-plan.md`

## 4. Individual Task File Structure

Each task file follows the template at `maestro-templates/task-file.md`. Required sections include:

- **Header**: Task ID, title, phase, status, dependencies, complexity, related ADRs.
- **Description**: One paragraph describing what the task accomplishes.
- **Acceptance Criteria**: Testable, atomic criteria.
- **Implementation Plan**: Numbered concrete steps for the production agent.
- **Evidence Requirements**: What proves the task is complete.
- **Known Risks**: Risks and mitigations.
- **References**: Spec, plan, and ADR pointers.
- **Session History**: A table populated as sessions execute.

**Template**: `maestro-templates/task-file.md`

### 4.1 Task File Lifecycle

- **Created**: during the setup session by Bernstein.
- **Updated**: at the end of every task session. The Session History table gains
  a new row with date, status change, head SHA, PR URL, and handoff path.
- **Never deleted**: persists for the life of the phase as part of the evidence trail.

## 5. Bernstein's Setup Directives

### 5.1 Before Creating the Phase Plan

1. Read global objectives — confirm the phase's goal and exit gate.
2. Read master roadmap — confirm the phase's position.
3. Read the product spec for relevant sections.
4. Read the ADRs that constrain this phase's scope.
5. Confirm the previous phase's post-phase session is complete.
6. Confirm the previous phase's maintenance phase is complete.

### 5.2 While Creating the Phase Plan

1. Decompose the phase goal into leaf tasks (each ≤ 1 PR).
2. Order tasks by dependency graph (no circular dependencies).
3. Assign P-ID numbers sequentially from 001.
4. Estimate complexity (S ≤2 agent turns, M ≤5, L >5).
5. Write acceptance criteria that are testable and atomic.
6. Create the individual task file for each task.

### 5.3 After Creating the Phase Plan

1. Create the phase workspace directory.
2. Update the master roadmap.
3. Produce the setup handout.
4. Terminate the setup session.
5. The next session begins the first task.

---

## 6. Setup Handout

The setup handout follows the template at `maestro-templates/setup-handout.md`. It carries:
- Phase identity (number, title, goal, exit gate)
- Task roster (IDs, titles, statuses, dependencies)
- First task key (path to the first pending task file)
- External context keys (paths to global docs, spec, ADR register)
- Workspace path

**Template**: `maestro-templates/setup-handout.md`

## 7. Quick Reference

| Situation | Action |
|---|---|
| Starting a new phase | Run the setup session per this document |
| Setup completes | Terminate. Next session = first task |
| Task file needs updating | Update Session History table at session end |
| Phase plan needs reordering | Allowed — do not rename P-IDs |
| New task needed mid-phase | Append with next available P-ID |
| Phase goal changes | Requires user confirmation; update header |
| Previous phase post-phase missing | HALT — post-phase is BLOCKING |
